CHAPTER VI

Engineering

平台开发全貌 —— 做一个交易平台需要掌握什么

这是把前五章的知识落到工程上的一章。一个能承接真实资金的交易平台，本质上是一个 要求极致一致性、极致性能、且必须具备金融级审计能力的分布式系统。 这里梳理九大核心模块、技术选型、以及绕不开的合规门槛。

01

系统总体架构

先把全貌画出来。交易平台的复杂度不在单个模块，而在模块之间的数据一致性与延迟约束。

核心系统分层

接入层 · Gateway

处理 WebSocket / REST / FIX 协议接入，负责鉴权、限流、连接管理、请求签名校验。Go / Netty / Rust

业务层 · Order Service

订单校验（余额、杠杆、价格精度、风控规则）、订单状态机、与撮合引擎通信。Go / Java

核心层 · Matching Engine

内存中的订单簿，单线程处理以保证确定性。这是整个系统对延迟最敏感的部分。C++ / Rust / Java（无 GC 停顿）

账务层 · Ledger Service

复式记账，处理成交后的资金划转、手续费、盈亏结算。必须保证幂等与强一致。Go / Java + 关系型数据库

风控层 · Risk Engine

实时保证金计算、强平触发、限额检查、异常交易检测。Rust / C++ / Go

行情层 · Market Data

K 线聚合、深度快照、成交推送。高并发广播，允许最终一致。Go / C++ + 消息队列

钱包层 · Custody

链上充提、地址管理、冷热钱包调度、多签审批。Go / Python + HSM

数据层 · Storage

热数据内存 + 关系库持久化 + 时序库存行情 + 数据仓库做分析与对账。PostgreSQL / Redis / ClickHouse

一条关键的架构原则

慢的东西不能挡住快的东西。撮合必须全内存、单线程、无外部依赖；持久化、通知、清算等操作通过事件流异步处理。一旦撮合路径上出现一次数据库写入或网络调用，延迟就从微秒变成毫秒 —— 在交易领域这是两个世界。

02

账务系统 · 整个平台最不能出错的地方

行情延迟高一点，用户抱怨；撮合慢一点，体验变差； 但账务出一次错，就是资金损失、信任崩塌、甚至法律问题。这是唯一必须做到零误差的模块。

核心原则一 · 复式记账

每一笔资金变动都要同时记录借方与贷方，任何时刻「所有账户余额之和」必须恒等于零（或恒等于已知的总量）。 这个约束提供了一个可自动校验的健全性检查 —— 任何 bug 或攻击都会立刻被对账发现。 

用户 A 用 1000 USDT 买入 0.015 BTC（手续费 1 USDT）

借：用户A-现货-可用-USDT        1,000
贷：用户A-现货-冻结-USDT        1,000
借：用户A-现货-冻结-USDT        1,000
贷：平台-交易对账-USDT          1,001
贷：平台-手续费收入-USDT            1  ← 注意：这里要反着记
...
──────────────────────────────────────────
最终结果：
  用户A: -1,000 USDT  +0.015 BTC
  对手方: +1,000 USDT  -0.015 BTC
  平台:   +1 USDT（手续费）

验证：所有科目变动之和 = 0  ✓

核心原则二 · 幂等性

网络会重试，消息会重复投递。同一个「成交回报」可能被处理两次。账务操作必须带唯一业务 ID， 重复执行时结果与执行一次完全相同，而不是扣两次钱。 

-- 幂等键：trade_id + account_id + asset
-- 唯一索引保证同一笔成交对同一账户只入账一次
CREATE UNIQUE INDEX uk_ledger_idem
  ON ledger_entries (trade_id, account_id, asset);

-- 插入时若冲突则忽略，天然幂等
INSERT INTO ledger_entries (...)
VALUES (...)
ON CONFLICT (trade_id, account_id, asset) DO NOTHING;

核心原则三 · 并发控制

行级锁

对账户行加悲观锁，简单可靠，但高并发下容易争抢。

乐观锁 + 版本号

读取版本号，更新时校验。冲突则重试，适合读多写少。

单线程串行化

同账户的操作路由到同一分区串行处理，彻底消除竞态。

绝对不要做的事

用浮点数存金额。永远用整数（最小单位）或 DECIMAL。浮点的舍入误差在累积几十亿笔交易后会变成真实资金缺口。 例如 0.1 + 0.2 != 0.3 在 IEEE 754 下是事实。BTC 用「聪」（1e-8），USDT 用 6 位小数整数。

03

撮合内核 · 整个系统的心脏

撮合引擎的职责是：接收订单、维护订单簿、按价格优先时间优先匹配、输出成交结果。 它的性能指标通常以微秒衡量，而它的正确性要求是零容忍。

设计要点做法原因
单线程处理 每个交易对一个线程，订单串行进入 避免锁竞争与竞态，保证结果确定性、可重放
全内存订单簿 价格档位用数组/跳表/红黑树维护 内存访问纳秒级，磁盘毫秒级，差 6 个数量级
避免动态分配 对象池预分配，避免运行时 GC/内存分配 GC 停顿会造成不可预测的延迟尖峰
无锁队列通信 订单通过环形缓冲区传入引擎 消除跨线程同步开销
CPU 亲和性绑定 引擎线程绑定独占核心，隔离中断 避免上下文切换与缓存失效
顺序日志 WAL 所有事件先写顺序日志再处理 崩溃后可精确恢复，用于审计与回放

核心数据结构

// 价格档位（Price Level）：同一价格上的所有订单按时间排队
type PriceLevel struct {
    Price      int64      // 用整数存储，避免浮点误差
    TotalQty   int64      // 该档位总量，用于深度展示
    Orders     *OrderList // FIFO 链表，保证时间优先
}

// 订单簿（OrderBook）：买单降序、卖单升序
type OrderBook struct {
    Bids    []*PriceLevel  // 买盘，价格由高到低
    Asks    []*PriceLevel  // 卖盘，价格由低到高
    BestBid *PriceLevel
    BestAsk *PriceLevel
}

// 撮合主循环（简化）
func (ob *OrderBook) Match(taker *Order) []Trade {
    var trades []Trade
    for taker.Remaining > 0 {
        var maker *Order
        if taker.Side == BUY {
            if ob.BestAsk == nil || taker.Price < ob.BestAsk.Price {
                break   // 无法成交，转为挂单
            }
            maker = ob.BestAsk.Orders.Front()
        } else {
            if ob.BestBid == nil || taker.Price > ob.BestBid.Price {
                break
            }
            maker = ob.BestBid.Orders.Front()
        }
        qty := min(taker.Remaining, maker.Remaining)
        trades = append(trades, Trade{Maker: maker, Taker: taker, Qty: qty})
        // 更新双方剩余量，若 maker 成交完则出队
    }
    return trades
}
确定性是关键要求

给定相同的输入序列，撮合引擎必须永远产出相同的结果。这不仅是正确性问题 —— 它是「可回放」的前提：崩溃后用日志重放，能精确恢复到故障前一刻的状态，不会产生重复成交或丢失成交。

04

行情与推送 · 把变化送到几十万人面前

数据的四个层次

  • Ticker 摘要 · 最新价、24 小时涨跌、成交量。更新频率低，全量广播
  • 深度 Depth · 订单簿快照 + 增量更新。可用「快照 + 增量」模式大幅降低带宽
  • 成交 Trades · 每一笔撮合结果，实时推送
  • K 线 Candles · 按周期聚合，通常由成交数据离线或流式合成

推送技术

  • WebSocket · 主流方案，双向长连接，服务端主动推送
  • 增量更新 · 只推送变化的价格档位，而非整本订单簿
  • 序列号机制 · 每个消息带序号，客户端检测丢包并请求补发
  • 分级订阅 · 用户可选 100 档或 400 档深度，按需推送降低负载
「快照 + 增量」是标准做法

先推送一份完整的订单簿快照（带序列号 N），之后只发变化的部分（N+1, N+2…）。 客户端本地维护订单簿副本。这样既保证了一致性（序列号连续可校验），又把带宽压到最低。若检测到序列号跳跃，客户端重新拉取快照。

05

风控与清算

事前风控

  • 余额与保证金充足性检查
  • 单笔/累计下单限额
  • 价格偏离保护（防止乌龙指）
  • 持仓上限与杠杆上限
  • 频率限制与异常行为拦截

事中监控

  • 实时保证金率计算
  • 强平触发与执行调度
  • 标记价格与指数价格监控
  • 市场异常波动告警
  • 大额订单与可疑账户追踪

标记价格：为什么不能直接用最新成交价

如果强平依据「最新成交价」，那么攻击者只需在流动性差的时刻用一笔小额订单把价格打到极端位置， 就能触发大量强平并从中获利。标记价格（Mark Price）用现货指数 + 资金费率基差计算出一个更稳健的价格， 专门用于计算盈亏与触发强平，与成交价解耦。

价格类型用途计算方式
最新成交价展示、行情最近一笔撮合价格
标记价格计算盈亏、触发强平多交易所现货指数 + 基差移动平均
指数价格标记价格的输入多家主流交易所价格的加权中位数
强平价格用户参考由开仓价、杠杆、维持保证金率反推
保险基金与 ADL 的必要性

极端行情下，强平单可能因流动性枯竭而无法以好价格成交，产生穿仓损失。 平台需要保险基金吸收这部分缺口；当基金不足时，启用自动减仓（ADL）， 强制平掉盈利最多的对手仓位来填补。这套机制虽然对个体不公平，但它是保护平台免于破产的最后一道防线。

06

钱包与资金安全 · 最容易被攻破的一环

平台持有的是用户真实资产。历史上交易所被盗的案例远多于被攻击的案例中平台能全额赔付的。 钱包架构的设计质量，直接决定平台能活多久。

热钱包

Hot Wallet

联网，用于处理日常提币。只保留满足日常提现的少量资金（通常不超过总资产的 2%~5%）。

风险最高，必须严格限额

温钱包

Warm Wallet

半离线，用于热钱包补充。需要人工审批与多签，自动化程度较低。

平衡安全与效率

冷钱包

Cold Wallet

完全离线，私钥永不接触网络。存放绝大部分资产，动用需多人多签、线下审批。

最安全，但操作缓慢

多重签名

采用 M-of-N 方案：例如 3-of-5 表示 5 把密钥中需要至少 3 把同时签名才能完成转账。 密钥分散到不同人、不同地理位置保管，任何单点泄露或内部人员作恶都无法单独转移资产。

安全措施作用实现方式
冷热分离限制单次损失上限95%+ 资产离线存储
多重签名防止单点失守3-of-5 密钥分散保管
HSM 硬件模块私钥不可导出签名在硬件内完成
提币风控拦截异常提现地址白名单、延迟到账、人工复核
地址校验防止地址替换攻击提币地址二次确认 + 前端防篡改
储备金证明向用户证明资产充足Merkle 树证明用户余额被包含
链上监控及时发现异常流出大额转账实时告警

技术栈全景

模块推荐技术选型理由
撮合引擎 C++ / Rust 无 GC 停顿、可精确控制内存布局与 CPU 亲和性
订单与业务服务 Go / Java (Netty) 并发模型成熟，开发生态好，性能足以支撑网关层
账务系统 Go / Java + PostgreSQL 强事务支持，ACID 保证，配合整数金额类型
风控引擎 Rust / C++ 极致低延迟，要求微秒级响应
行情推送 Go / C++ + WebSocket 高并发长连接管理，支持百万级连接
消息队列 Kafka / NATS / Pulsar 事件流解耦，支持顺序保证与重放
缓存 Redis 热点数据、分布式锁、限流计数
时序数据 ClickHouse / TimescaleDB 海量行情与成交记录的高效存储与查询
链上交互 Go-Ethereum / Web3.js / Rust 节点通信、交易构造与广播、事件监听
密钥管理 HSM / Vault / MPC 私钥隔离、签名服务化、多方计算
前端 React / Vue + Canvas / WebGL K 线图高性能渲染，深度图实时更新
可观测性 Prometheus + Grafana + Jaeger 指标、日志、链路追踪三位一体
语言选择的实质

不是「哪个语言最好」，而是「这段代码的延迟要求是什么」。撮合路径要求个位数微秒，必须用无 GC 的语言； 业务逻辑要求开发效率与正确性，Go/Java 更合适。用 Go 写撮合能跑，但会损失一个数量级的延迟优势。

08

非功能要求 · 这些比功能更难做到

维度目标关键手段
延迟 撮合 P99 < 1ms 内存撮合、CPU 绑定、无锁队列、内核旁路网络
吞吐 10 万+ TPS 分片（按交易对）、水平扩展网关、异步持久化
可用性 99.99% 多活部署、故障自动切换、跨机房容灾
一致性 账务零误差 复式记账、幂等设计、定时全量对账
可审计 全链路可追溯 事件溯源、不可篡改的审计日志、只追加设计
可恢复 RPO=0 / RTO<1min WAL 顺序日志、定期快照、自动重放恢复
安全性 防内外攻击 最小权限、双人复核、密钥隔离、渗透测试
「账务零误差」意味着什么

假设平台有 100 万个账户，每账户每天 100 笔操作，一年就是 365 亿次记录。 错误率必须低于百亿分之一才能真正做到「零误差」。这就是为什么账务系统必须用最保守的设计 —— 宁可慢，不可错；宁可拒绝请求，不可产生不确定状态。

09

合规与牌照 · 真正的门槛在这里

技术可以招人解决，合规不能。这是绝大多数交易平台项目真正的生死线。

中国大陆的监管立场

根据中国人民银行等部门发布的相关通知，虚拟货币相关业务活动属于非法金融活动。 在中国境内开设虚拟货币交易所、提供撮合与衍生品交易服务、为虚拟货币交易提供支付结算服务，均不被允许。 任何在中国境内面向公众运营虚拟币交易平台的设想，在合规层面都不成立。

监管要求内容工程实现
KYC 实名认证 身份核验、地址证明、风险评级 证件 OCR、活体检测、第三方风控接口
AML 反洗钱 可疑交易监测与上报 规则引擎 + 链上地址风险评分
CFT 反恐融资 制裁名单筛查 实时名单比对与拦截
交易报告 大额与可疑交易报送 自动化报表生成与上报接口
资金隔离 客户资产与平台资产分离 独立账户体系 + 定期第三方审计
数据留存 交易与身份数据保存若干年 冷存储 + 加密归档
牌照资质 部分地区需 VASP / MSB 等许可 法务与政府事务，非工程问题
成本量级

在允许的司法辖区申请合规牌照，周期通常在 6~24 个月，直接成本从数十万到数百万美元不等， 且需要持续的合规团队与审计支出。这笔投入往往超过整个技术团队的成本 —— 这是行业最真实的一面。

10

如果真要做，路线图长什么样

顺序很重要。先做能验证核心机制的闭环，再叠加复杂功能。

第一阶段 · 账务内核

先做复式记账系统，加幂等与对账。用单元测试与不变量校验（账目恒为零）保证正确性。 不要急着做界面 —— 账目错了，界面再好看也没意义。

第二阶段 · 撮合引擎

实现内存订单簿与价格优先时间优先匹配。用历史数据做回放测试，验证确定性与性能。 目标：百万订单回放结果完全一致。

第三阶段 · 现货闭环

打通下单 → 撮合 → 账务 → 行情推送的完整链路。此时已经可以支撑现货交易。

第四阶段 · 钱包与充提

接入区块链节点，实现地址生成、充值监听、提币签名。建立冷热钱包体系与多签审批流程。

第五阶段 · 风控与合约

加入保证金计算、强平引擎、保险基金。上线永续合约 —— 复杂度显著高于现货，必须建立在前四个阶段稳固的基础上。

第六阶段 · 期权与做市

引入期权定价、希腊字母风控，以及做市商体系。这是最高阶的部分，需要专门的量化与衍生品团队。

贯穿全程 · 安全与合规

安全审计、渗透测试、KYC/AML、牌照申请必须并行推进，而不是等到最后补。很多项目死在「功能做完了但拿不到许可」。

最后必须说明
